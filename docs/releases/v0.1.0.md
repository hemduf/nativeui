# NativeUI v0.1.0 — developer preview

NativeUI v0.1.0 is a **developer preview** of the framework's reusable core, native-view integration and low-level installed CMake package. It is not the NativeUI 1.0 product-completeness or API-stability release. Public API and package details **may change** incompatibly during the 0.x series; T071 owns the later NativeUI 1.0 qualification gate.

## Supported v0.1 platforms

- macOS, using Cocoa/Pugl and the consumer-scoped Objective-C bridge;
- Windows x64/MSVC, using Win32/Pugl;
- Linux x64/X11, using X11/Pugl.

Wayland is not part of the v0.1 supported platform set.

## Build requirements and pinned dependencies

NativeUI requires CMake 3.24 or newer and a C++20 compiler. Platform SDK prerequisites are:

- macOS: Xcode or Command Line Tools;
- Windows: MSVC/Windows SDK and OpenGL support;
- Linux/X11: X11, OpenGL/GLX and Fontconfig development packages.

The release build acquires dependencies through the repository CMake configuration. The release candidate is pinned to:

- Pugl source commit `d12d63815b8cfe3f36293d3791a418e8f558ff1b`;
- `skia-builder` release tag `chrome/m149`, with a platform/configuration-specific SHA-256 for every supported artifact.

The T052 clean-bootstrap gate starts from an empty dependency cache on macOS, Windows and Linux/X11. The release source contract also requires the Skia `URL_HASH` enforcement path and exercises a deliberate SHA-256 mismatch to ensure the underlying CMake download primitive fails closed with a hash-mismatch diagnostic.

## Low-level installed-package contract

After installing NativeUI, an external final consumer uses the v0.1 low-level package like this:

```cmake
find_package(NativeUI CONFIG REQUIRED)

add_executable(MyApplication main.cpp)
target_link_libraries(MyApplication PRIVATE NativeUI::Core)
nativeui_attach_platform(
    TARGET MyApplication
    CONSUMER_ID com.example.my-application
)
```

`NativeUI::Core` is generic. `nativeui_attach_platform()` attaches the supported native platform layer to an existing final executable/shared/module target. `CONSUMER_ID` is mandatory on every platform. On macOS it also drives the deterministic consumer-scoped Objective-C runtime namespace; consumers must not restore a global/manual Pugl runtime prefix.

T047 and T048 qualify this package through independent relocated install-tree consumers. Native consumers do not need a separately installed Pugl package or NativeUI private source paths.

## v0.1 qualification contract

The release tag must point to the exact source commit qualified by all of the following gates:

1. normal CI on Linux/X11, Windows/MSVC and macOS plus Linux ASan+UBSan;
2. relocated T047/T048 package consumers and the macOS two-consumer Objective-C class/metaclass/runtime-isolation checks carried by normal CI;
3. T042 deterministic lifecycle/multi-instance stress on all currently supported ownership paths;
4. T052 clean-cache dependency bootstrap on the three supported desktop platforms;
5. T051 Release benchmarks on the exact candidate SHA, including the zero `idle_invalidation` hard gate and immutable JSON evidence;
6. the T052 source/release contract and aggregate `CODE_REVIEW.md` audit with no Blocking or Important finding.

T052 measures one run from the approved/base commit and two complete runs from the exact candidate on the same runner. Timing or allocation regressions block only under the frozen T051 two-candidate-run policy. Once that comparison passes, the candidate run artifacts become the controlled v0.1 baseline evidence. The benchmark executable never rewrites that baseline; later comparisons must preserve T051 metadata compatibility and threshold rules.

## Standalone ownership boundary

The v0.1 standalone compatibility path supports one top-level `PUGL_PROGRAM` world per process/application lifetime. Issue #64 froze **Decision B** after deterministic macOS failure evidence from multiple independent PROGRAM worlds. Simultaneous top-level windows therefore require the future explicit application-level owner in T060; v0.1 does not hide this behind a mutable process-global singleton or `thread_local` workaround.

Independent embedded `PUGL_MODULE` views remain the supported plug-in/editor-style multi-instance path and are covered by T042 stress.

## Known v1 gaps

The developer preview deliberately does not claim NativeUI 1.0 completeness. Notable work still outside the v0.1 gate includes:

- T060's explicit application/shared-PROGRAM multi-window ownership API;
- the remaining standard widget, selection/container and higher-level application work after the current Button/Checkbox/Radio baseline;
- the remaining styling/theme/animation roadmap;
- later accessibility/platform-service qualification and the full T071 NativeUI 1.0 gate;
- Wayland support;
- plug-in-format-specific build helpers or SDK ownership.

These gaps do not weaken the package/core/lifecycle guarantees actually qualified by T052; they are explicit exclusions from v0.1 scope.

## Reproducible tag procedure

1. Refresh the T052 candidate branch from current `main` and resolve documentation/roadmap conflicts without dropping newer work.
2. Run the complete T052 exact-head validation set and record the workflow/run evidence in the T052 PR review.
3. Perform the mandatory aggregate `CODE_REVIEW.md` audit on that exact head.
4. Create tag `v0.1.0` on that exact validated source commit. Do not retarget the tag after validation.
5. Integrate the release-gate PR without rewriting the tagged source commit, so the validated/tagged commit remains reachable from `main` history.
6. Publish release notes from this document and retain the T052/T051 artifacts as qualification evidence.

If any source change is required after step 2, the candidate SHA changes and every exact-head release gate must be rerun before tagging.
